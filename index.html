A real SNES routine · ActRaiser (1990) · $00:984E–$00:9883

Three ways to run the same 54 bytes

Emulation, recompilation and decompilation get mixed up all the time. This page takes one real routine from ActRaiser, a 1990 SNES game, and shows it each way. The routine decides what the player’s character does next while standing still. The difference between the three comes down to when the game’s code gets translated, and how much machinery is still running underneath it while you play.

Who does the work, and when

All three end with the game running on your computer. What changes is when the game’s code gets translated, and what is still running underneath it while you play.

Pretend to be a SNES. The emulator reads the game’s machine code as data and carries out each instruction as it comes.

Translate the program once. A recompiler turns the machine code into C before you play. The compiled game runs natively on a layer that stands in for the SNES hardware.

One decision, three ways

Each frame the player stands still, the game runs these 20 instructions to decide what happens next. They check, in this order:

  1. Nothing underfoot: fall.
  2. B pressed and nothing overhead: jump.
  3. Down held: crouch.
  4. Left or Right held: run.
  5. Otherwise, stand still.

The live translator

  • This is the translator’s rulebook. It knows what every kind of instruction means, but nothing about this game.
  • This piece of the game runs about 60 times a second, and the translator works through it again every single time.
  • All that translating is extra work for your computer, on top of actually playing the game.

An emulator: the game is data, and a loop drives it

  • This code knows nothing about the game. case 0xAD runs both LDA $00A1 instructions here, and every other absolute LDA in the game.
  • Each time an instruction runs, the emulator fetches its bytes again and works out what they mean, down to whether it is 8-bit or 16-bit (cpu->m_flag ? … : …). That even decides how many bytes the instruction has.
  • The C compiler optimized this loop, not the game. It never sees that the three instructions at $985B together mean “is B pressed?”, so it can’t simplify them.
  • After every instruction, the graphics, sound and timers have to catch up so the whole console stays in step.

The pre-translated book

  • This piece was translated once, before you started playing. Each old instruction became a line or two of new code.
  • Nothing needs translating while you play, so your computer has much less extra work to do.
  • But it’s word for word. It still talks about the old machine’s parts, and it never says what any of it is for.

Recompiled: translated once, then compiled to native code

  • Each instruction became a line or two of C. The operands are now constants (0x00A1, 0x0080), and branches are gotos to labels named after ROM addresses.
  • Nothing reads or decodes the game’s bytes while you play. The C compiler sees the game’s own logic and optimizes it like any other C.
  • It still behaves like a SNES CPU. Registers and flags live in a struct, and mem_read16(cpu->db, 0x00A1) goes through the translation layer, which maps SNES addresses onto emulated memory and hardware.
  • The translation is exact but nameless. Nothing here says “jump” or “ground”, because the recompiler never learned what any of it means.

Illustrative. Real recompiler output has this shape, but is usually noisier, with extra bookkeeping for calls, interrupts and debugging.

Rewritten in plain words

  • Someone worked out what this piece is for and rewrote it so people can read it.
  • It reads almost like a sentence: if there’s no floor, fall. If you pressed jump and nothing is above you, jump.
  • Because it’s clear, it’s easy to fix, change, or add new moves to.

Decompiled: rewritten as ordinary code

  • The decision in these 20 instructions became five lines. Names replace numbers: bit $80 of $00A1 is jump_pressed, and the carry flag after JSR $8FE7 is on_ground.
  • There are no registers, flags, addresses or ROM. It is a plain function you can read, test and change without any model of the SNES.
  • The rules are easy to see now. Falling beats everything, a low ceiling cancels a jump, and crouching beats running.
  • It can grow past the original. A new move is one more line, and nothing here depends on SNES timing or memory layout.

Illustrative. The names are chosen by whoever does the decompiling. A faithful decompilation keeps the original’s order of side effects, which is why the two probe results arrive as inputs instead of being called in here.

Real projects mix all three

These aren’t exclusive choices. A recompiled game still needs something to play the part of the hardware, a project can leave some chips emulated, and decompiled code can replace recompiled code one routine at a time.

  • RecompiledThe main CPU’s game code
  • Translation layerMemory map, graphics, DMA and timing
  • EmulatedCoprocessors, such as the SNES’s SPC700 sound CPU
  • DecompiledGameplay, one routine at a time
